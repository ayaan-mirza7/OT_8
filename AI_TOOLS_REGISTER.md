## 2. Documented Failure Log (AI Errors Found, Verified, and Corrected)

### Case 1: Track B Combinatorial Solvers — `scipy.optimize.milp` Bounds Unpacking TypeError
- **AI Tool:** Gemini 3.8 Flash (Antigravity)
- **Initial Generated Code:**
  ```python
  bounds = [(0, 1) for _ in range(problem.n)]
  res = milp(c=c, constraints=constraints, integrality=integrality, bounds=bounds)
  ```
- **Observed Failure:** Run-time crash with `TypeError: Bounds.__init__() takes from 1 to 4 positional arguments but 17 were given` followed by `ValueError: bounds must be convertible into an instance of scipy.optimize.Bounds`.
- **Root Cause:** In modern SciPy (`>=1.10.0`), `milp` expects `scipy.optimize.Bounds` with array lower/upper bounds `Bounds(lb=0.0, ub=1.0)` or vector arrays, rather than a list of tuples as used in legacy `linprog(method='highs')`.
- **Engineering Fix Applied:**
  ```python
  from scipy.optimize import Bounds
  bounds = Bounds(lb=0.0, ub=1.0)
  ```
- **Lesson Learned:** Modern numerical libraries frequently modernize parameter APIs. Never assume AI tool training data reflects the exact signature changes in recent package updates; always verify against installed library documentation.

### Case 2: Track D Federated Learning — Label Vector Dimension Mismatch in Binary Cross-Entropy
- **AI Tool:** Gemini 3.8 Flash
- **Initial Generated Code:**
  ```python
  def compute_loss_and_grad(w: np.ndarray, X: np.ndarray, y: np.ndarray, l2_reg: float = 1e-3):
      N = len(y)
      logits = X @ w
      p = 1.0 / (1.0 + np.exp(-np.clip(logits, -12.0, 12.0)))
      grad = (X.T @ (p - y)) / N + l2_reg * w
  ```
- **Observed Failure:** `ValueError: operands could not be broadcast together with shapes (4, 300) (4,)`.
- **Root Cause:** When `y` was initialized with shape `(N, 1)` but `w` had shape `(D,)`, `logits` was 1D of shape `(N,)`. Subtracting `(N,) - (N, 1)` triggered 2D outer broadcasting creating `(N, N)`, yielding incorrect matrix dimension `(4, 300)` on transposition.
- **Engineering Fix Applied:**
  ```python
  y_flat = y.ravel()
  grad = (X.T @ (p - y_flat)) / N + l2_reg * w
  ```
- **Lesson Learned:** High-dimensional mathematical formulations generated by LLMs often blur 1D arrays and 2D single-column matrices. Enforcing strict vector dimension checks (`.ravel()` or `.squeeze()`) is mandatory in matrix calculus code.

### Case 3: Track H DBMS Optimization — SQLite Secondary Index Ignored by Query Planner
- **AI Tool:** Gemini 3.8 Flash
- **Initial Generated Code:**
  Created compound indexes on `(l_shipdate, l_discount)` and ran queries without updating SQLite catalog statistics:
  ```python
  cur.execute("CREATE INDEX idx_lineitem_ship_disc ON lineitem(l_shipdate, l_discount);")
  # immediately ran benchmark
  ```
- **Observed Failure:** In SQLite, the query planner output remained `SCAN lineitem` (full sequential table scan) instead of `SEARCH lineitem USING INDEX`, causing a negative speedup (0.79x due to un-analyzed overhead).
- **Root Cause:** SQLite's cost-based query planner relies on internal statistics table `sqlite_stat1`. Without running `ANALYZE;`, the optimizer assumes high cost for index lookups over small-to-medium tables and prefers sequential scan.
- **Engineering Fix Applied:**
  ```python
  cur.execute("ANALYZE;")
  conn.commit()
  ```
  Immediately transformed execution to:
  `SEARCH lineitem USING INDEX idx_lineitem_ship_disc (l_shipdate=? AND l_discount<?)` delivering a **165.4x speedup** on Q1 and **3.15x overall workload speedup**.
- **Lesson Learned:** Database optimizers are heuristic and cost-driven. Simply generating index definitions without understanding planner catalog statistics will cause optimizations to fail silently in production.
